# Word 公式生成与排版避坑实战手册

在撰写高质量工程规范、系统方案报告与学术技术文档时，数学公式的排版质量直接影响文档的专业度与严肃性。本文档系统总结将 Markdown 中的 LaTeX 数学公式无损渲染为 Word 原生可编辑公式（OMML）的完整工程链路，并针对实战中高频出现的乱码、方框、基线错位等缺陷提供根治方案。

---

## 一、 公式生成的技术路线对比

| 维度 | 方案 A：原生 Office Math (OMML)（推荐） | 方案 B：公式图片渲染 (PNG / SVG) | 方案 C：原始 LaTeX 源码回退 |
| :--- | :--- | :--- | :--- |
| **呈现形态** | Word 原生矢量可编辑数学对象 (`m:oMath`) | 栅格位图或矢量图片嵌入 | 原始代码纯文本字符串 |
| **排版质感** | 字体自适应、随字号自然伸缩、矢量无损 | 打印或高分屏模糊、容易产生锯齿 | 缺乏可读性、排版原始 |
| **行内对齐** | **完美自适应垂直基准线（Baseline）** | **行高突变、公式向上或向下悬空** | 与普通文本一致 |
| **二次编辑** | 在 Word / WPS 中双击即可直接修改公式 | 无法编辑，修改必须重新生成图片 | 需重新排版 |
| **技术审查友好** | 评审专家与同行可直接复制公式符号或验算 | 无法提取符号，二次复核成本高 | 不符合正式交付标准 |

**工程选型铁律**：除用户明确要求的特殊场景外，**一律采用原生 OMML 方案**。

## 二、 OMML 转换链路与标准流程

```text
┌─────────────────────────────────────────────────────────────┐
│ 1. Markdown 源码 (含 $...$, $$...$$, \(...\), \[...\])      │
└──────────────────────────────┬──────────────────────────────┘
                               │ 正则提取与文本规范化
┌──────────────────────────────▼──────────────────────────────┐
│ 2. LaTeX 表达式规范化清洗 (命令归一化、去除多余外壳)         │
└──────────────────────────────┬──────────────────────────────┘
                               │ latex2mathml 转换
┌──────────────────────────────▼──────────────────────────────┐
│ 3. 结构化 MathML XML DOM                                    │
└──────────────────────────────┬──────────────────────────────┘
                               │ 映射为 Office Math 命名空间节点
┌──────────────────────────────▼──────────────────────────────┐
│ 4. OMML 节点生成 (m:oMath / m:oMathPara)                    │
└──────────────────────────────┬──────────────────────────────┘
                               │ 递归清洗空节点、容错修正
┌──────────────────────────────▼──────────────────────────────┐
│ 5. python-docx 段落挂载 (直接写入 word/document.xml)         │
└─────────────────────────────────────────────────────────────┘
```

## 三、 实战高频缺陷原因与避坑指南

### 坑 1：公式右上角出现虚线小方框 / 问号乱码（如 $\mathbf{\Sigma}^{\square}$、$\dot{q}^{\square}$）
- **现象特征**：Word 打开后，符号右上角或右下角出现一个虚线小方框，或者转换为 PDF 时出现带有问号的占位符。
- **根本原因**：
  1. MathML 映射为 OMML 时，未能正确区分 `m:sSup`（单上标）、`m:sSub`（单下标）与 `m:sSubSup`（双上下标）。把单上标误写成了双标结构，导致其下标分支 `m:sub` 内部没有实际文字节点；
  2. 生成的底数元素 `m:e` 内部为空。Word 的数学渲染引擎遇到空的容器节点时，会强制渲染一个浅灰色/虚线的占位方框提示用户输入。
- **根治对策**：
  - 严格根据 MathML 的节点类型构建对应的 OMML 标签；
  - 在写入段落前，对生成的 OMML XML 执行深度递归扫描，**无条件清除所有空的 `m:sub`、`m:sup`、`m:e` 节点**，确保每个数学容器内部均有真实的文本 (`m:t`)。

### 坑 2：数学字体回退与彩色小字符
- **现象特征**：矩阵符号或粗体向量（如 $\mathbf{y}$）在 Word 或导出 PDF 时，显示为异常的彩色字体、间距过大的宽字符或直接丢失。
- **根本原因**：LaTeX 中的 `\mathbf`、`\mathsf`、`\mathbb` 等字符在直接转为特定 Unicode 字符块时，Windows 或 Linux 系统中的目标公式字体（如 Cambria Math）缺少对应字形，触发字体回退（Font Fallback），Office 会临时调用系统的 Emoji 字体或其它第三方字体补齐。
- **根治对策**：
  - 在转入 OMML 时，优先使用 OMML 自身的字体修饰属性（如 `<m:rPr><m:scr m:val="..."><m:sty m:val="b"/></m:rPr>`）来定义粗体/斜体，而不是依赖外部生僻的 Unicode 专用数学字母块。

### 坑 3：LaTeX 源码裸露在正文中（如 `\( y = \mathbf{\Sigma}_t^{-1} x_t ... \)`）
- **现象特征**：Word 正文中没有公式，而是直接显示了未转义的 LaTeX 代码。
- **根本原因**：
  - 正则表达式匹配不全（例如转换脚本仅识别了 `$...$`，遗漏了 `\( ... \)` 或 `\[ ... \]`）；
  - 行内公式跨行换行，导致单行正则匹配失败；
  - 公式内存在未闭合的括号或非法转义，导致 `latex2mathml` 抛出异常后被捕获但未妥善处理，直接将原文本写入文档。
- **根治对策**：
  - 正则必须同时支持 `$...$`、`$$...$$`、`\(...\)`、`\[...\]`；
  - 统一在 Markdown 编写阶段规范公式标记：**行内公式统一采用 `$公式$`，独立行公式统一采用 `$$公式$$` 或 `\[公式\]`**；
  - 交付前执行裸露标记静态扫描，严禁正文中出现未解析的 LaTeX 语法标记。

### 坑 4：正则清洗命令“误伤词根”
- **现象特征**：包含 `\left`、`\limits` 的公式在转换时报错崩溃或解析混乱。
- **根本原因**：为了兼容 LaTeX 简写，写了类似 `latex.replace(r"\le", r"\leq")` 的无边界全局替换，直接将 `\left` 替换成了 `\leqft`！
- **根治对策**：
  - 所有 LaTeX 宏命令替换必须带有词边界或正则前瞻判断，例如：
    ```python
    import re
    # 仅当 \le 后面不是英文字母时才替换为 \leq
    body = re.sub(r"\\le(?![A-Za-z])", r"\\leq", body)
    body = re.sub(r"\\ge(?![A-Za-z])", r"\\geq", body)
    ```

### 坑 5：行内公式使用位图破坏排版美感
- **现象特征**：文档正文的行间距忽大忽小，公式图片与周围汉字上下错位，视觉效果极为廉价。
- **根本原因**：把行内公式渲染为 PNG 插图，由于图片底边默认对齐文字基线，文字与图片无法居中。
- **根治对策**：
  - **行内公式全面使用原生 OMML**。在 Word 中，原生 OMML 公式与段落文本同属于一个流式排版系统，排版引擎会自动将公式中线与文字中线对齐，保持行距绝对均匀整齐。

## 四、 自动化质检五步法

在生成 DOCX 后，必须执行以下自动化质检流程，确保零缺陷交付：

```bash
# 1. 扫描 Markdown 中是否存在未闭合或裸露的 LaTeX 标记
# 确保所有公式均符合规范

# 2. 运行带 OMML 统计的转换脚本
# 检查转换日志，确保 OMML 成功率 100%，回退计数为 0

# 3. 解压 docx 检查 XML 中的空节点（彻底杜绝方框）
python3 -c "
import zipfile, xml.etree.ElementTree as ET
with zipfile.ZipFile('output.docx') as z:
    root = ET.fromstring(z.read('word/document.xml'))
    empty_sup = len([e for e in root.iter() if e.tag.endswith('sSup') and len(e) < 2])
    empty_sub = len([e for e in root.iter() if e.tag.endswith('sSub') and len(e) < 2])
    print(f'Empty sup: {empty_sup}, Empty sub: {empty_sub}')
    assert empty_sup == 0 and empty_sub == 0, '存在空上下标节点，将导致方框乱码！'
"

# 4. (可选) 利用 LibreOffice 转 PDF 做最终跨平台视觉复核
soffice --headless --convert-to pdf output.docx

# 5. 检查页面中无渲染替代字符或空白占位
```
