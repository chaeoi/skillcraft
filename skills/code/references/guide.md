# 实用主义 Vibe Coding 指南

本指南系统性总结在多类软件项目、工具链与工程实践中沉淀的高效开发哲学与工程规范，供后续协作开发时严格遵循。

## 开发画像与核心习惯

### 1. 仓库按可交付边界拆分

- 坚持“一仓库对应一个能独立理解、构建、部署或发布的主题”，而不是把所有功能塞进一个巨型 monorepo。
- 独立项目各自拥有完整的 README、配置、测试和发布入口；相关组件只有在确实共享生命周期时才放在同一个仓库。
- 仓库根目录保持高度可导航：入口文件、README、构建文件、配置样例和部署文件放在显眼位置；业务代码、静态资源、测试、脚本和文档按职责进入对应目录。
- 目录拆分服务于维护和交付，不追求形式上的层级。小项目可以只有 `index.html`、`assets/`、`data/`；复杂项目再拆成 `core/`、`app/`、`agent/`、`functions/`、`tests/` 等边界清晰的目录。
- 服务边界通常对应实际运行边界：Dashboard 与 Agent 分开，语音处理链路按识别/合成/模型路由/编排拆分，硬件驱动与上层应用分开；每个进程都应有明确输入、输出、配置和健康状态。

### 2. 静态优先，布局直接可读

- Web 工具类默认从纯静态方案开始：根目录有 `index.html`，样式和脚本分别放在 `assets/css`、`assets/js` 或同等清晰的位置，图片、图标和业务数据各自归档。
- 页面布局围绕内容和任务展开，不为了使用框架而引入框架。HTML 负责结构，CSS 负责视觉和响应式，JavaScript 负责交互、数据加载、路由和状态。
- 需要多个视图时优先使用简单的 hash 路由、查询参数或独立静态页面；刷新、分享和浏览器前进后退应能恢复用户看到的筛选条件。
- 内容型站点采用静态生成器时，也保持内容、布局、静态资源、配置文件和主题覆盖的职责分离；生成后的结果应能直接托管。
- 数据驱动页面优先把可变内容放在 JSON/YAML 等数据文件中，由脚本渲染列表、图表或配置项，避免把大量重复数据硬编码到模板里。
- 只有在确实需要复杂图表、高强度编码、语法高亮等能力时才引入第三方前端库；大型公共资源可通过 CDN 管理，但要明确版本并保留可理解的本地结构。
- 静态页面也必须具备加载中、空数据、失败、移动端适配、长文本截断和无脚本时的合理表现；“静态”指部署极简，不代表可以忽略交互健壮性。

### 3. 前后端分离，契约清楚

- 偏好前端静态托管、后端独立运行：前端可使用 Pages 或轻量反向代理，后端采用高性能微服务（如 Go、FastAPI 等）。
- 前端只负责展示、交互输入和轻量状态；认证鉴权、会话持久化、数据一致性、模型调度、文件校验等核心业务由服务端保证，避免把关键逻辑散落在浏览器。
- API 必须先定义资源、路径、方法、请求/响应数据结构、HTTP 状态码、认证方式和错误格式，再连接 UI；流式传输场景优先使用 SSE/WebSocket 等明确协议。
- CORS、Cookie/JWT、Bearer token、Origin、代理头和缓存策略都是接口契约的必要组成部分，绝不靠前端“默认能用”来掩盖协议缺陷。
- 前端与后端保持独立发布和替换能力，配置来源、版本兼容、健康检查和本地联调命令必须写清楚。
- 浏览器本地能高效完成且不需要服务端状态的任务，优先本地处理（如媒体预览、客户端压制、本地配置解析与轻量筛选），以最小化服务端和带宽开销。

### 4. 追求最小资源占用和最短运行链路

- 资源占用是关键设计约束：能用静态文件就不启动服务，能用浏览器本地计算就不上传，能用嵌入式存储/KV 就不额外部署数据库，能用单进程就不拆成多个常驻微服务。
- 依赖数量、镜像体积、启动时间、内存、磁盘和网络流量都要有意识地控制；不为了“标准架构”添加暂时没有价值的消息队列、缓存层、复杂 ORM 或繁重的前端构建链。
- 生产镜像倾向多阶段构建、最小基础镜像、静态编译、非 root 用户、只读文件系统、明确数据卷和健康检查；不需要的工具、端口、权限和运行时文件不进入镜像。
- 存储按用途分层：配置与控制数据持久化，历史数据按保留策略管理，临时缓存可丢弃；默认值、目录、权限和备份方式必须明确。
- 性能优化优先消除无效工作：按需加载、合理采样和降采样、流式传输、边缘缓存、避免重复请求、限制并发和及时释放资源。
- “最小”绝不等于牺牲可靠性。必要的输入校验、重试退避、错误回滚、诊断日志、健康检查和边界测试必须严格齐备。

### 5. 文档与交付真实透明

- 项目必须具备清晰简洁的 README，说明运行前置条件、启动命令、配置示例与测试方法。
- 变更说明使用直接、具体的工程语言，说明“修改了什么行为、为什么、如何验证”，严禁空泛的公关套话。
- 坚决杜绝在示例与提交中泄露密钥、内部专用网络地址或真实凭证。

### 6. 彻底杜绝 AI 感、机械感与需求复述

- **前端与文案**：绝不使用“欢迎使用智能助手”、“赋能全流程”、“全方位智能化”等虚浮空洞口号；页面占位符、空状态与按钮文案必须是具体、真实、专业的工程用语；严禁直接把用户的提示词或需求长句原样粘贴为页面副标题。
- **代码与注释**：绝不写机械复述语法或重复需求的低效注释（如“定义一个函数”、“从用户需求读取”）；只在存在不易察觉的算法不变量、特殊协议时序约束或潜在边界陷阱时写简短原因；绝不留下“由 AI 生成”等元标记。
- **交互与沟通**：直接陈述核心方案与验证结果，严禁机械重复用户指令（如“好的，按照您的要求，我将为您...”）；始终保持精炼、高效、专业的人类资深工程师语调。

## 一句话总结

实用主义开发哲学是：用最短的反馈周期，把真实需求做成可部署、可验证的轻量系统；随后围绕运行时事实、数据正确性、安全边界和维护成本持续打磨，直到工具不仅能演示，而且能高可靠地长期运行。
